# Citation Suggestion Mechanism & Technical Assessment

## Overview

TarCite (TarCite Workspace) is a **local-first academic citation assistant** that takes a paragraph written by a researcher and suggests which papers from their personal library should be cited — complete with verbatim evidence quotes, confidence ratings, and pre-formatted citations.

The pipeline has two major phases: **Ingestion** (building the searchable index from PDFs) and **Query** (turning a paragraph into ranked citation suggestions).

---

## Phase 1: Document Ingestion (Indexing)

### 1.1 PDF Scanning & Metadata Extraction

- The app scans a user-configured directory for PDF, RIS, and BibTeX files.
- **PyMuPDF (fitz)** extracts full text from each PDF.
- A dedicated **first-page parser** identifies headers, authors, DOI, abstract, and journal information from the first page of academic papers.
- If a DOI is found, the app queries the **Crossref API** to enrich metadata (authors, journal, citation count).
- All metadata is stored in **SQLite** (~25 tables).

### 1.2 Sentence-Aware Text Chunking

- Extracted text is split into overlapping chunks of **~900 characters** with **200-character overlap**.
- Splitting is **sentence-aware** (splits at `.!?` boundaries) so chunks never cut mid-sentence.
- Minimum chunk length: **60 characters**.
- Each item produces chunks from three source types: **abstract**, **notes** (HTML stripped), and **fulltext**.

### 1.3 Dual Indexing

Each chunk is indexed in **two parallel systems**:

| Index | Technology | Purpose |
|-------|-----------|---------|
| **Vector Store** | ChromaDB (HNSW, cosine similarity) | Semantic search — finds conceptually related text |
| **Full-Text Index** | SQLite FTS5 (BM25, Porter stemmer) | Keyword search — finds exact term matches |

- Embeddings are generated by **sentence-transformers** (default: `all-MiniLM-L6-v2`, 384-dim). Users can also use `BAAI/bge-large-en-v1.5` or any OpenAI-compatible API.
- Hardware acceleration: auto-detects **MPS (Apple Silicon)**, **CUDA (NVIDIA)**, or falls back to **CPU**.

## Phase 2: Citation Suggestion Pipeline

When the user pastes a paragraph and clicks "Suggest", a **7-stage pipeline** executes:

### Stage 1: HyDE — Hypothetical Document Embeddings

Before searching, the system uses the LLM to generate a **hypothetical ideal cited passage** — a 2-4 sentence passage that a relevant source might contain. This hypothetical passage is embedded and used as the vector search query instead of the raw paragraph.

**Why this matters:** There is often a vocabulary gap between what the user writes and how academic papers are written. HyDE bridges this gap by transforming the paragraph into "paper-like" language, improving semantic matching recall by 10-20%.

If HyDE generation fails, the system gracefully falls back to the raw paragraph.

### Stage 2: Parallel Triple Retrieval

Three retrieval strategies run **concurrently**:

- **Vector Search** (ChromaDB): Cosine similarity between the HyDE-generated query vector and all chunk vectors. Distance threshold: 0.85.
- **BM25 Keyword Search** (SQLite FTS5): Traditional information retrieval using the BM25 ranking function with Porter stemming. Matches exact terms and phrases.
- **Title Search** (SQLite): Keyword matching against paper titles in the items table. Papers whose titles match query terms receive a significant boost.

These three approaches are complementary:
- Vector search catches **conceptual similarity** ("neural networks" matches "deep learning architectures")
- BM25 catches **exact terminology** ("CRISPR-Cas9" must match "CRISPR-Cas9")
- Title search catches **topical relevance** (papers about "transformer attention" surface when the paragraph discusses attention mechanisms)

### Stage 3: Weighted Reciprocal Rank Fusion (RRF)

The three ranked lists are merged using **Weighted RRF**:

- Each chunk's fused score = sum of `weight / (k + rank)` across all ranked lists, where k=60.
- Vector and BM25 streams use weight **1.0**; title stream uses weight **2.0** — giving title-matched papers a strong boost since title relevance is a high-confidence signal.
- RRF is rank-based (not score-based), making it robust to different score scales between retrieval methods.
- Papers found via title search but not in chunk results are included as candidates with their abstract as evidence.
- Chunks are then **grouped by paper** (using item_key), keeping the top **6 chunks per paper**.
- Each group is enriched with full metadata from SQLite.

### Stage 4: Cross-Encoder Reranking

- A **CrossEncoder model** (`cross-encoder/ms-marco-MiniLM-L-6-v2`, ~66 MB) scores each (paragraph, evidence) pair jointly.
- Unlike bi-encoder cosine similarity, the cross-encoder processes both texts together with full cross-attention, yielding significantly higher accuracy.
- Up to **1024 characters** of each paper's best evidence is used for scoring (expanded from 512 for richer context).
- The top-K candidates (default: 50) are returned, sorted by rerank score.

### Stage 5: MMR Diversity Selection

After reranking, **Max Marginal Relevance (MMR)** ensures the final candidate set is diverse:

- Each candidate is re-evaluated with: `score = λ × relevance - (1-λ) × max_similarity_to_already_selected`
- λ = 0.7 by default (70% relevance, 30% diversity)
- Relevance comes from the reranker score; diversity is measured by cosine distance between candidate embeddings
- This prevents redundant suggestions (e.g., 5 papers all saying the same thing) and ensures the user sees sources covering different aspects of their paragraph

### Stage 6: LLM Evaluation & Citation Formatting

The diverse, reranked candidates are sent to an **LLM** (OpenAI-compatible — supports GPT-4, Ollama, Kimi, etc.) for final evaluation.

**What the LLM receives:**
- The paragraph to cite
- Each candidate source with: title, authors, year, DOI, journal, pre-formatted APA inline citation, pre-formatted full reference, and up to 6 evidence passages (with source type and similarity score)

**What the LLM is instructed to do:**
- Select the most relevant sources and rank them
- Extract **verbatim evidence quotes** (not paraphrased)
- Rate **confidence** (High / Medium / Low) based on how directly the source supports the claim
- Rate **evidence coverage** (strong / partial / single_point) based on breadth of support
- Return structured JSON

**Anti-Hallucination Safeguards:**
- The system prompt explicitly forbids inventing citations
- Every returned `item_key` is validated against the actual retrieved source list — fabricated citations are silently removed
- Citations are **pre-formatted server-side** (not by the LLM) to prevent formatting drift
- If the LLM returns invalid JSON, the system retries with a stricter prompt, then attempts JSON repair (closing unclosed strings/brackets)

### Stage 7: User Feedback

Each suggestion displays **thumbs up / thumbs down** buttons in the card header:

- Users can accept (thumb up) or reject (thumb down) each suggestion
- Clicking an active thumb again **undoes** the feedback (toggle)
- Feedback is persisted in SQLite (per run_id + item_key) for future ranking improvements
- API: `POST /api/suggestion-feedback` with `{ run_id, item_key, feedback_type }` where type is `thumb_up`, `thumb_down`, or `none`

## Key Design Strengths

| Aspect | Assessment |
|--------|-----------|
| **Query Expansion** | HyDE bridges the vocabulary gap between user-written text and academic paper language, improving recall significantly without requiring the user to reformulate their paragraph. |
| **Retrieval Quality** | Triple-stream hybrid retrieval (vector + BM25 + title) with weighted RRF fusion is robust. Title matching provides a strong topical relevance signal that pure chunk-level search can miss. |
| **Reranking Accuracy** | Cross-encoder reranking with 1024-char evidence input captures richer context for more accurate scoring. The model is small (~66 MB) but effective. |
| **Result Diversity** | MMR ensures suggestions cover different aspects of the paragraph, not just variations of the same finding. λ=0.7 balances relevance with diversity. |
| **Hallucination Prevention** | Multi-layered: strict system prompt rules, server-side citation pre-formatting, post-LLM item_key validation, and removal of fabricated citations. |
| **Feedback Loop** | Thumb-based feedback is persisted and available for future ranking personalization. Simple binary signal ensures high user adoption. |
| **Privacy** | All data and embeddings stay local. Only the LLM calls (HyDE generation + final evaluation) optionally send text externally. Users can use Ollama for fully offline operation. |
| **Graceful Degradation** | HyDE falls back to raw paragraph. If reranker fails, results use RRF order. If FTS5 is empty, vector+title search runs. If LLM returns bad JSON, retry + repair attempts are made. |

## Potential Limitations

| Aspect | Note |
|--------|------|
| **Chunk size is fixed** | 900 chars may be too small for long-form arguments or too large for abstract-only papers. Adaptive chunking could improve precision. |
| **Cross-encoder bottleneck** | Reranking is CPU-bound (unless GPU available). For very large candidate sets, this could slow down the pipeline. |
| **HyDE latency** | The extra LLM call adds ~1-3s to the pipeline. Using a fast model mitigates this, but it's still an additional cost. |
| **LLM dependency** | Final evaluation quality depends entirely on the chosen LLM. Smaller local models (e.g., 3B parameters) may produce less accurate confidence calibration or miss subtle relevance. |
| **Single language** | The embedding models and FTS5 stemmer are English-focused. Non-English papers may have lower retrieval quality. |
